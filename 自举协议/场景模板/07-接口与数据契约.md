# AGENTS.md · 接口与数据契约协议（Contract）

> 适用场景：前后端联调、多服务对接、Agent 与工具/外部 API 对接、字段口径不一致。
> 用法：复制到目标项目根目录改名为 `AGENTS.md`，并叠加「维护协议」第 0 节。

## 1. 触发与退出条件

**触发**：两个及以上模块需要交换数据；或联调时出现「字段对不上」「格式不一致」。

**退出（DoD）**：
- 契约**先于代码**存在：一份 OpenAPI / 类型定义 / schema，作为唯一事实来源。
- 两端都能基于契约独立开发，且契约测试通过。
- 错误码、空值、时区、精度语义写清楚，不需要口头确认。

## 2. 硬性规则

1. **契约先行**：先定字段、类型、必填、错误码，再写两端实现。
2. **单一事实来源**：类型/schema 只在一处定义，其他端由它生成或导入，禁止两端各写一份。
3. **口径必须写死**：
   - 时间：统一 UTC 或本地时区，统一格式（ISO8601 / 时间戳）
   - 金额：单位与精度（分 / 元，小数位）
   - ID：类型（string / number）、是否可为空
   - 枚举：穷举取值，未知值处理策略
4. **错误码枚举化**：禁止魔法字符串；每个错误码有含义、HTTP 状态、可重试性。
5. **变更必须兼容**：改字段走版本号或兼容期，禁止静默改字段含义/类型。
6. **Mock 与真实实现同契约**：mock 不得「看起来对」，必须能被同一份契约测试校验。

## 3. 标准流程

1. **对齐需求口径**：双方列出各自理解的字段含义，逐条对齐差异。
2. **写契约**：产出 schema / 类型定义 / 接口文档，提交评审。
3. **生成骨架**：客户端与 mock 由契约生成。
4. **并行开发**：两端基于 mock / 契约测试独立推进。
5. **真联调**：接真实服务，跑契约测试。
6. **收尾**：把契约位置与变更规则写入 `AGENTS.md`。

## 4. 交付前自检

```
<契约测试命令>        # 请求/响应均符合 schema
<类型检查命令>        # 前端类型与契约一致
```

- 空值、缺省、异常返回是否有明确约定？
- 新增/修改字段是否向后兼容？

## 5. 反模式

- 边联调边改契约，两端永远对不上。
- 字段含义靠口头约定，文档不写。
- 用 `any` / 动态字典绕过契约。
- 错误只返回 500 + 字符串，无法区分原因。
