# AGENTS.md · 文档与上下文沉淀协议（Knowledge）

> 适用场景：做技术决策、踩坑、跨会话/跨人交接、需要长期维护的项目。
> 用法：复制到目标项目根目录改名为 `AGENTS.md`，并叠加「维护协议」第 0 节。

## 1. 触发与退出条件

**触发**：出现「换人、换 Agent、换机器也必须知道」的信息；或完成一个需求/修复。

**退出（DoD）**：
- 该留的信息已写入正确位置（`AGENTS.md` 或 `docs/`），且无重复条目。
- 决策有记录（ADR）：选了什么、为什么不选替代方案。
- 文档与代码在同一次变更中更新。

## 2. 硬性规则

1. **只写换人也必须知道的**：技术决策及原因、用户纠正过的点、跨模块数据口径、禁改区、隐蔽的坑、交付前自检命令。
2. **不写**：项目介绍、功能说明、本次实现细节、未经验证的猜测（不确定先问）。
3. **先检索再写入**：有同类条目则修订合并，失效或被推翻的删除，禁止重复追加。
4. **章节自然生长**：不预设结构；超过 150 行时细节拆到 `docs/rules/*.md`，主文件只留总纲与链接。
5. **决策用 ADR**：重要选型/架构变更写 `docs/adr/NNNN-标题.md`，含背景、选项、决定、后果。
6. **文档不写未来时**：不写「以后会支持」，只记录当前事实。

## 3. 标准流程

1. **判断价值**：这条信息是否影响他人后续决策？否则不写。
2. **定位**：规则/约束 → `AGENTS.md`；决策 → `docs/adr/`；长细节 → `docs/rules/`。
3. **去重**：检索关键词，确认没有重复条目。
4. **写入**：一条一事，简洁、可执行。
5. **同步提交**：与代码改动同一次提交。
6. **告知**：用一行说明新增/修改/删除了哪条。

## 4. 交付前自检

- `AGENTS.md` 是否超过 150 行？超了就拆分。
- 是否有重复或已失效的条目？
- 决策是否都有 ADR 或记录出处？
- 文档中的命令是否仍能执行？

## 5. 反模式

- 写流水账、写实现细节、写复制来的通用大道理。
- 同类条目重复堆叠，越写越长越没人看。
- 文档过期不删，误导后来者。
- 代码改了文档不改。
- 把猜测写成事实。
