# AGENTS.md · 需求澄清协议（Discovery）

> 适用场景：需求模糊、口头描述、边界不清、用户只说「做个类似 XX 的东西」。
> 用法：复制到目标项目根目录改名为 `AGENTS.md`，并叠加「维护协议」第 0 节。

## 1. 触发与退出条件

**触发**：无法把需求直接写成验收标准；或同一句话有两种以上合理解释。

**退出（DoD）**：
- 有一份可评审的需求卡（见第 3 节模板），且用户确认过。
- 每条验收标准都是**可测量**的（能写成测试或可观察结果）。
- 明确了「不做什么」（非目标），避免范围蔓延。

## 2. 硬性规则

1. **必问三件事**：谁用 / 什么算完成 / 边界外是什么。
2. **只问阻塞项**：把歧义列成清单并按影响排序，一次只问会改变实现方向的问题，不超过 3 个。
3. **方案化不确定**：需求不明时给 2～3 个方案 + 取舍，让用户选，不要抛开放性大问题。
4. **禁止「我觉得应该是」**：默认值、边界行为、异常处理都必须得到确认或写入「假设」。
5. **假设必须显式**：拿不准但必须先推进的，写成「假设：…，若不符请纠正」，并在交付时复述。

## 3. 需求卡模板

```
目标：<一句话，解决谁的什么问题>
用户故事：作为 <角色>，我希望 <行为>，以便 <价值>
验收标准：
  - Given <前提> When <操作> Then <可观察结果>
  - Given <前提> When <操作> Then <可观察结果>
非目标：<明确不做的范围>
关键假设：<拿不准但先按此推进的点>
风险：<依赖 / 数据 / 权限 / 兼容性>
```

## 4. 交付前自检

- 需求卡中的每条验收标准，是否都能对应到一个可执行的验证步骤？
- 「非目标」是否写清楚了？
- 所有假设是否已告知用户，且用户没有反对？

## 5. 反模式

- 边写代码边补需求，最后和用户预期不符。
- 把「实现方案」当成「需求」直接开工。
- 一次抛出二十个问题把用户问烦。
- 遇到歧义自己拍板，不告知。
