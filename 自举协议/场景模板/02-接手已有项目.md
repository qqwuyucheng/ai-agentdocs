# AGENTS.md · 接手已有项目协议（Brownfield）

> 适用场景：进入他人仓库、历史遗留系统、换人接手、跨团队协作。
> 用法：复制到目标项目根目录改名为 `AGENTS.md`，并叠加「维护协议」第 0 节。

## 1. 触发与退出条件

**触发**：进入一个不是自己从零写的仓库；或用户说「这是我们之前做的，你看看」。

**退出（DoD）**：
- 本地能**完整跑起来**（服务、数据库、依赖、环境变量）。
- 产出一份「风险地图」：哪些能改、哪些绝对不能碰、哪些是黑盒。
- 在未破坏原有行为的前提下，完成并验证一个小改动。

## 2. 硬性规则

1. **先读后写，建立可运行基线前禁止改任何业务代码**。跑不起来先修环境，不碰业务逻辑。
2. **动手前先写「我的理解」并让用户确认**：一句话说清这个模块干什么、你要改哪里、影响谁。
3. **不顺手重构**：不格式化无关文件、不升级无关依赖、不改命名风格。
4. **先标记禁改区**：数据库迁移脚本、生产配置、密钥、自动生成代码、第三方 patch —— 除非用户明确授权。
5. **改动最小化**：一次只动一个关注点，能不改的文件就不改。
6. **不猜业务语义**：字段含义、历史逻辑不清楚时，先查提交记录和文档，仍不清就问。

## 3. 标准流程

1. **盘点**：目录结构、README/docs、`git log -20`、CI 配置、依赖清单。
2. **跑通**：按文档启动；文档缺失就边跑边补一份「实际启动步骤」。
3. **画风险地图**：核心链路 / 数据流向 / 外部依赖 / 禁改区 / 已知坑。
4. **验证一次改动**：选一个低风险小改动，走完「改 → 测 → 回滚演练」。
5. **再进入正式开发**，并把过程中的坑写入本项目 `AGENTS.md`。

## 4. 交付前自检

```
git status            # 确认没有误改无关文件
<原有测试命令>        # 必须仍全绿
<启动命令>            # 手动验证原有功能未回归
```

## 5. 反模式

- 上来就大范围改代码或全局格式化。
- 假设「看起来像那样」，直接按猜测改业务规则。
- 因为编译不过就升级一堆依赖。
- 删除或覆盖看不懂的历史逻辑。
- 不记录启动步骤，下次又要重新摸索。
